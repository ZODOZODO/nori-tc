# TC Business Core App 요구사항 동결 (Step 1)

## 1. 문서 목적
이 문서는 `tc-business-core-app` 구현 착수 전에 합의된 요구사항과 정책을 고정하기 위한 기준 문서입니다.
구현/리팩터링 시 본 문서를 단일 기준으로 사용합니다.

## 2. 책임 범위
- Kafka 입력 토픽 소비
  - `tc.eqp.events`
  - `tc.mes.events`
  - `tc.ui.events`
- Kafka 출력 토픽 발행
  - `tc.eqp.commands`
  - `tc.mes.commands`
  - `tc.ui.commands`
- 메시지 순차 처리 단위는 `eqpId`
- `eqpId -> modelKey -> TcModelRuntime` 메모리 캐시 기반 워크플로우 처리
- UI 이벤트 처리 후 `tc.ui.commands`로 REP 발행

## 3. 확정 정책

### 3.1 eqpId 정책
- `eqpId`는 UI Backend 정책으로 반드시 포함됩니다.
- Business Core는 `eqpId` 누락 케이스를 정상 입력 시나리오로 간주하지 않습니다.

### 3.2 순차성 정책
- 순차성/격리 기준은 `eqpId`입니다.
- `inFlight=1`은 동시성 제어만 담당합니다.
- `inFlight`는 작업 완료(`finally`) 시 항상 해제됩니다.

### 3.3 workflow 미존재 정책
- 매칭되는 workflow가 없으면 `warn` 로그를 남기고 정상 종료합니다.
- 실패/재시도/DLQ 대상이 아닙니다.

### 3.4 DLQ 정책
- 재시도 한도 초과 또는 영구 실패 시 DLQ 발행합니다.
- DLQ 메시지는 `payloadRef`만 포함합니다.
- DLQ로 이동된 건은 `inFlight`와 결합하지 않습니다.
- DLQ 수동 처리 여부와 무관하게 다음 메시지는 계속 처리됩니다.

### 3.5 Timeout 정책
- Task 실행 시간 제한은 3분입니다.
- 3분 초과 시 실행 스레드 `interrupt()` 후 재시도 정책으로 이관합니다.
- 재시도 한도 초과 시 DLQ로 이관합니다.

### 3.6 설비 중단 정책
- 설비 중단/재개 정책의 최종 책임은 MES에 있습니다.
- TC 내부에서 DLQ 처리 상태를 이유로 설비를 강제 정지시키지 않습니다.
- 즉, `inFlight`를 설비 중단 상태 제어 수단으로 사용하지 않습니다.

### 3.7 데이터 소스 정책
- 초기 설계/구현은 DB만 사용합니다.
- JAR 로딩 소스도 초기에는 DB 기준으로 설계합니다.

## 4. UI REP 정책
- `tc.ui.events` 소비 후 결과 REP는 반드시 `tc.ui.commands`로 발행합니다.
- 성공/실패 모두 REP를 발행합니다.
- REP 발행 실패는 재시도 후 정책에 따라 처리합니다.

## 5. 공통화 원칙 (요구사항 레벨)
- 공통 모듈은 알고리즘/런타임 골격만 담당합니다.
- 도메인 규칙(업무 해석, workflow 의미, 장비 제어 의미)은 앱 계층에서 담당합니다.
- 공통 모듈은 특정 앱 패키지에 직접 의존하지 않습니다.

## 6. 변경 관리
- 본 문서의 정책 변경은 합의 후 명시적으로 버전 업데이트합니다.
- 구현 중 정책 충돌이 확인되면 코드보다 본 문서를 우선 수정/재합의합니다.
