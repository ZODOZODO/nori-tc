# Next Nori TC Architecture

> 본 문서는 고객 제안서 성격으로 작성한 `nori-tc` 차세대 제품 아키텍처 설명 자료입니다.
> 목적은 `nori-tc`가 어떤 고객 문제를 해결하는지, 현재 어떤 기반을 이미 갖고 있는지,
> next 단계에서 무엇을 추가 구현하려는지, 그리고 고객사가 도입했을 때 어디서 비용이 줄어드는지를
> 한 문서에서 이해할 수 있게 설명하는 것입니다.
>
> 본 문서의 표기 기준은 아래와 같습니다.
>
> - `현재 기반`: 현재 코드, 스키마, 운영 규칙, 내부 설계 문서로 근거를 확인할 수 있는 항목
> - `next 단계`: 현재 기반 위에 추가 구현이 필요한 항목
> - `AI 활용`: `LLM + RAG + AI Agent` 기준으로 설명

---

## 1. nori-tc 한 줄 정의

`nori-tc`는 설비를 단순 연결하는 TC가 아니라, 신규 설비 도입 속도, 운영 변경 안정성, 메시지 처리 증명 가능성, 운영 설명 가능성, 이후 EDA/FDC 확장성을 함께 고려한 **라인 실행 플랫폼**입니다.

---

## 2. 왜 지금 nori-tc 인가

고객 현장에서 TC는 이미 필수 시스템입니다. 따라서 단순 연결, 기본 모니터링, 일반적인 모델/설비 관리 기능만으로는 더 이상 차별화가 어렵습니다.

고객이 실제로 비용을 지출하는 지점은 아래와 같습니다.

- 신규 설비 도입이 늦어 생산 일정이 밀리는 비용
- 변경 배포 중 라인이 흔들려 생산 손실이 발생하는 비용
- 장애 원인 파악이 늦어 MTTR이 길어지는 비용
- 메시지 유실, 중복 처리, 반쪽 처리 여부를 증명하지 못해 운영 리스크가 커지는 비용
- 이후 EDA(Equipment Data Acquisition, 설비 데이터 실시간 고속 수집), FDC(Fault Detection and Classification, 공정 이상 감지 및 분류), 상위 분석 시스템을 붙일 때 다시 구조를 뜯어고치는 비용

`nori-tc`는 이 비용 구조를 줄이기 위해 아래 6개 우선순위 키워드를 중심으로 제품을 설계합니다.

## 3. 우선순위별 핵심 키워드

| 우선순위 | 키워드 | 고객이 얻는 가치 | AI 활용 위치 | 직접 줄어드는 비용 |
|---|---|---|---|---|

## 4. 키워드별 상세 설명

## 4.1 `Spec-to-Proof`

### 고객 문제

신규 설비 도입 프로젝트에서 가장 시간이 많이 드는 구간은 설비사 문서 해석, 메시지 규칙 정리, parser 작성, workflow 초안 작성, 테스트 준비입니다. 특히 설비사 문서는 PDF/Word 설명서, Excel 표, XML 예시, 샘플 로그가 섞여 있고, 누락이나 모호한 표현이 많아 개발자 개인 역량 의존도가 높습니다.

### 적용 방식

`Spec-to-Proof`의 핵심은 사람이 설비사 문서를 다시 수작업으로 정리하는 것이 아니라, `원본 문서 -> 근거 데이터 -> 검토 가능한 명세` 흐름으로 바꾸는 것입니다.

동작 순서는 아래와 같습니다.

1. 고객사는 설비사 문서 원본(PDF/Word), Excel, XML, 샘플 로그를 그대로 입력합니다.
2. `nori-tc`는 파일 형식별 추출 어댑터를 통해 1차 추출을 수행합니다.
   - Excel / XML은 구조가 비교적 명확하므로 규칙 기반 파서로 우선 처리합니다.
   - PDF / Word / 스캔 문서는 외부 문서 분석 엔진 또는 로컬 라이브러리를 추출 어댑터로 연결해 처리합니다.
   - 샘플 로그는 line, timestamp, messageName, field token 기준으로 분해합니다.
3. 여기서 중요한 점은 `nori-tc`가 모든 파서를 직접 새로 만드는 것이 아니라, 검증된 외부 파서나 문서 분석 서비스를 포함해 사용할 수 있도록 `추출 어댑터 계층`을 제공하는 것입니다.
4. 추출 결과는 `evidence block`이라는 공통 구조로 정규화합니다.
   - `evidence block`은 단순 텍스트 청크가 아니라, 원본 위치와 구조 정보를 함께 가진 근거 단위입니다.
   - 예: `file`, `page`, `section`, `sheet`, `cellRange`, `line`, `content`, `parserType`, `confidence`
5. 내부의 단일 기준 데이터는 자유 형식 `md`가 아니라 이 `구조화된 evidence / spec 데이터`입니다.
   - `md`나 결과서는 사람이 검토하기 위한 산출물일 수 있지만, 시스템이 직접 사용하는 기준 데이터는 아닙니다.
6. `RAG`는 이 evidence block과 함께 내부 모델 스키마, 기존 설비 온보딩 사례, 메시지 규칙, workflow 패턴, 검증 규칙을 참조합니다.
7. `LLM`은 이 근거와 참조 지식을 바탕으로 `메시지 규칙`, `workflow`, `action`, `검증 포인트`의 초안을 생성합니다.
8. `AI Agent`는 여러 입력 파일을 교차 검토해 누락 필드, 상충 규칙, 미확정 항목을 정리하고, 사람에게 확인받아야 할 질문 목록을 만듭니다.
9. 사람 검토와 설비사 확인을 거쳐 승인된 명세만 parser 초안, workflow 초안, 테스트 시나리오, 결과서 초안 생성으로 연결합니다.
10. 실제 런타임 반영은 승인된 명세 기준으로만 진행합니다.

즉, `nori-tc`가 하려는 일은 “문서 파일을 그냥 LLM에 던져서 답을 받는다”가 아니라, `형식별 추출 -> evidence 정규화 -> RAG/LLM 초안 생성 -> Agent 교차검토 -> 사람 승인` 흐름을 제품 기능으로 제공하는 것입니다.

### 현재 기반

`Spec-to-Proof`의 AI 흐름이 동작하려면, LLM이 생성한 초안을 어디에 어떤 형태로 채워 넣어야 하는지가 사전에 명확히 정의되어 있어야 합니다. `nori-tc`는 이 기반이 이미 갖춰져 있습니다.

- **모델 스키마 정의 완료**: 메시지 타입, 파라미터, workflow, MDF(Master Data File)의 구조와 필드 정의가 이미 확정되어 있어, LLM이 생성한 명세를 매핑할 타겟 스키마가 존재합니다. LLM은 빈 곳에 아무 형태로나 결과를 만드는 것이 아니라, 이미 정의된 스키마 형태에 맞춰 초안을 생성합니다.
- **모델 버전 관리 구조**: 승인된 명세가 어떤 버전에 반영되었는지 추적할 수 있는 버전 관리 구조가 있습니다.
- **조회 및 반영 API**: 모델, 메시지, workflow 초안을 생성한 뒤 시스템에 바로 반영할 수 있는 API와 UI 구조가 이미 존재합니다. 별도 연동 개발 없이 Spec-to-Proof 결과를 실제 운영 데이터로 연결할 수 있습니다.

### next 단계에서 추가할 것

- 문서 입력 / 추출 계층
- 형식별 추출 어댑터 계층
  - Excel/XML: 구조 기반 로컬 파서
  - PDF/Word/스캔 문서: 고객사 내부 환경에서 동작하는 문서 분석 라이브러리 연계
  - 샘플 로그: 라인/타임스탬프/필드 토큰 기준 분해
- `evidence block` 표준 스키마와 저장 구조
- RAG 인덱싱 계층 (모델 스키마, 기존 온보딩 사례, 검증 규칙 포함)
- 명세 초안 검토/승인 UI
- 승인된 명세 기반 parser / workflow / 테스트 결과서 초안 생성 기능

### 고객 관점의 의미

- 신규 설비 도입 시 문서 해석 시간이 줄어듭니다.
- 숙련 개발자 한 명에게 지식이 과도하게 집중되는 문제를 줄일 수 있습니다.
- 설비사와 확인해야 할 질문 목록이 구조화됩니다.
- 초안, 검토 포인트, 테스트 준비물이 같은 체계에서 연결됩니다.

### 비용 절감 포인트

신규 설비 통합 프로젝트에서 설비사 문서 해석부터 초기 통합 테스트 완료까지는 일반적으로 **4~8주** 이상 소요됩니다. 이 기간의 상당 부분은 문서 반복 해석, 누락 항목 확인을 위한 벤더 재질의, 초안 반복 작성에서 발생합니다.

`Spec-to-Proof`는 이 반복 작업 구간을 단축하는 것을 목표로 합니다.

- 설비 도입 프로젝트 리드타임 단축 (현장 경험 기준, 문서 해석 및 초안 작성 단계에서 **30~50% 단축** 가능)
- 벤더와의 재질의 / 재작업 감소 (누락 항목과 상충 규칙을 사전에 구조화)
- 숙련 개발자가 문서 해석에 투입되는 시간 감소
- 초기 통합 테스트 반복 비용 감소

## 4.2 `Verified ChangeOps`

### 고객 문제

운영 중인 라인에서 가장 큰 리스크는 기능 부재보다 `변경 실패`입니다. Model, Workflow, EQP 파라미터, Gateway 라우팅 규칙 중 하나만 잘못 반영되어도 생산 손실과 긴급 대응 비용이 커집니다.

### 적용 방식

`Verified ChangeOps`는 단순 버전 관리가 아니라, `변경 전 검증`, `반영 중 통제`, `반영 후 복구`를 하나의 운영 절차로 묶는 개념입니다.

동작 방향은 아래와 같습니다.

1. 변경 대상은 항상 `현재 운영 버전`과 `편집 버전`을 분리합니다.
2. 변경 내용은 사람이 읽을 수 있는 `diff`로 보여줍니다.
3. 어떤 EQP, 어떤 model version, 어떤 workflow, 어떤 gateway group에 영향이 가는지 계산합니다.
4. 운영 로그 또는 대표 샘플 데이터를 기준으로 사전 검증을 수행합니다.
5. 전체 반영이 아니라 일부 설비 또는 일부 gateway group부터 단계 반영합니다.
6. 이상 징후가 있으면 이전 버전으로 되돌릴 수 있는 절차를 함께 제공합니다.

여기서 AI는 핵심 실행 엔진이라기보다 보조 역할입니다.

- diff 요약
- 영향도 설명
- 검토 포인트 추천
- 변경 승인 문구 / 결과 요약 초안

실제 반영 통제와 버전 전환은 규칙 기반 메커니즘이 담당해야 합니다.

### 현재 기반

- 설비 파라미터는 `Check Out -> EDIT -> Save -> Check In` 구조를 이미 사용합니다.
- 모델도 `EDIT` 버전을 활용한 변경 흐름을 갖고 있습니다.
- 고정 partition 기반 gateway 라우팅 구조를 이미 갖고 있어 단계 배포 단위를 만들기 좋습니다.

### next 단계에서 추가할 것

- 변경 diff 표준화
- 영향도 계산 그래프
- 운영 로그 기반 사전 검증
- 단계 반영 계획 UI
- 이상 징후 감지와 복귀 절차 자동화

### 고객 관점의 의미

- 변경이 사람 기억이나 숙련도에 덜 의존하게 됩니다.
- 변경 승인 과정에서 “무엇이 달라졌는지”를 명확히 볼 수 있습니다.
- 운영 중 변경 사고 확률을 낮출 수 있습니다.

### 비용 절감 포인트

운영 중인 라인에서 하나의 변경 실패는 라인 중단으로 이어질 수 있으며, 라인 규모에 따라 중단 1시간당 수천만 원에서 수억 원의 손실이 발생합니다. 운영 현장 경험 기준으로 계획된 변경 작업의 **15~25%** 에서 예기치 않은 문제가 발생합니다.

`Verified ChangeOps`는 이 사고 확률을 낮추는 것을 목표로 합니다.

- 변경 사고로 인한 라인 중단 비용 감소 (diff와 영향도 사전 검증으로 사고 원인을 배포 전에 식별)
- 긴급 롤백 대응 비용 감소 (복귀 절차가 사전 준비된 경우 롤백 시간 **60~80% 단축** 목표)
- 변경 검토 / 승인 / 운영 이관 시간 감소

## 4.3 `Provable Reliability`

### 고객 문제

고객이 원하는 것은 단순히 “안정적입니다”라는 문장이 아닙니다. 메시지가 어디서 생성되었고, 어느 파티션으로 발행되었고, 누가 처리했고, 실패 시 어디에 남았는지까지 추적하고 설명할 수 있어야 합니다.

### 적용 방식

`Provable Reliability`는 안정성을 추상적 표현이 아니라, 관측 가능하고 재현 가능한 메커니즘으로 설명하는 방식입니다.

핵심 메커니즘은 아래와 같습니다.

1. Gateway 대상 메시지는 `tc_eqp.route_partition`를 단일 라우팅 기준으로 사용해 명시 partition 발행합니다.
2. 같은 PASSIVE listener-group은 같은 partition을 사용하도록 강제해 split-brain 가능성을 줄입니다.
3. `EQP_CREATE / UPDATE / DELETE`는 Gateway와 Business 양쪽 응답이 모두 도착해야 완료로 인정합니다.
4. `EQP_START / END`는 비동기 trace 단위로 추적하고 결과를 별도 저장합니다.
5. 처리 실패는 Gateway / Business DLQ에 격리해 추후 조사와 재처리가 가능하게 합니다.
6. traceId, eqpId, topic, partition, 상태 전이 정보를 연계해 조사 근거를 남깁니다.

Transactional Outbox 패턴은 신뢰성을 한 단계 더 강화하는 메커니즘입니다.

- outbox 테이블과 저장소 계층 구조는 이미 설계되어 있습니다.
- 현재는 안정적인 직접 발행 경로로 운영하며, next 단계에서 outbox 기반 발행으로 전환해 메시지 유실 가능성을 0에 가깝게 낮추는 것을 목표로 합니다.

즉, 현재의 실질 강점은 `route_partition`, `Dual Response`, `Async 결과 저장`, `DLQ` 메커니즘이며, outbox 전환은 그 위에 추가하는 신뢰성 강화 단계입니다.

### 현재 기반

- 고정 partition 라우팅 규칙
- Dual Response 수집 구조
- Async 결과 저장 구조
- Gateway / Business DLQ 구조
- Transactional Outbox 테이블과 발송 이력 구조

### next 단계에서 추가할 것

- 런타임 발행 경로와 outbox의 end-to-end 연결
- 재발행 워커
- 발송 이력 / 재시도 / dead 상태 운영 뷰
- 신뢰성 진단 대시보드

### 고객 관점의 의미

- 메시지 유실 의심 상황에서 근거를 제시할 수 있습니다.
- “어디서 끊겼는지”를 로그와 상태 기준으로 설명할 수 있습니다.
- 장애 대응과 감사 대응 품질이 올라갑니다.

### 비용 절감 포인트

메시지 유실이나 중복 처리 의심 건이 발생했을 때, 근거 없이는 조사만으로도 숙련 엔지니어 기준 **하루~수일**이 소요됩니다. `nori-tc`는 이 조사 구간을 단축합니다.

- 장애 재현 인건비 감소 (trace 기반 근거 조회로 재현 시간 단축)
- 유실 / 중복 의심 건 조사 시간 감소 (발송 이력과 DLQ 상태를 기반으로 빠른 원인 특정)
- 현장 신뢰 이슈로 인한 운영 리스크 감소 (증명 가능한 처리 근거로 고객사 내부 감사 대응 강화)

## 4.4 `Explainable Operation Intelligence`

### 고객 문제

운영 현장에서는 장애 자체보다 “무슨 일이 있었는지 설명하기 어렵다”는 점이 더 큰 비용이 됩니다. 로그는 많지만 사건 단위로 묶여 있지 않으면, 숙련 운영자만 상황을 복원할 수 있습니다.

### 적용 방식

`Explainable Operation Intelligence`는 운영 데이터 위에 `설명 가능한 사건 뷰`를 올리는 개념입니다.

동작 방향은 아래와 같습니다.

1. TC 로그, traceId, eqpId, modelVersion, workflow, runtime state, DLQ, 작업 이력 등을 사건 단위로 묶습니다.
2. 운영자가 보고 싶은 질문을 기준으로 사건 타임라인을 구성합니다.
   - 어떤 설비에서
   - 어떤 변경 이후
   - 어떤 메시지가 실패했고
   - 어떤 상태 전이가 있었고
   - 현재 영향 범위가 어디까지인지
   - 다음 대응은 무엇인지
3. `RAG`는 이 사건과 관련된 로그, 상태, 버전 이력, 작업 문맥을 함께 조회합니다.
4. `LLM`은 조회된 근거를 바탕으로 사건 설명, 가능한 원인, 확인해야 할 다음 조치를 정리합니다.
5. `AI Agent`는 필요한 경우 추가 조회를 반복하고, 근거가 부족한 부분은 `추정`으로 명확히 표시하거나 운영자 확인 질문으로 전환합니다.
6. 최종 화면은 자연어 설명만 보여주는 것이 아니라, 그 설명이 어떤 로그와 이벤트를 근거로 했는지 함께 보여줘야 합니다.

즉, 이 항목의 목적은 “AI가 마음대로 판단한다”가 아니라, `운영자가 추적해야 할 근거를 더 빨리 묶어주고 설명해주는 것`입니다.

### 현재 기반

- traceId 기반 요청 / 응답 추적 구조
- EQP runtime-state 조회 구조
- 작업(Work -> ControlJob -> ProcessJob -> Lot) 계층 구조
- 모델 / 워크플로 / 파라미터 버전 구조

### next 단계에서 추가할 것

- 사건 단위 타임라인 뷰
- 근거 링크가 포함된 자연어 설명
- 대응 체크리스트 생성
- 교대 근무 인수인계용 사건 요약

### 고객 관점의 의미

- 장애 원인 파악 시간이 짧아집니다.
- 운영자 숙련도 의존을 줄일 수 있습니다.
- 교대 근무 / 야간 대응에서 인수인계 품질이 올라갑니다.

### 비용 절감 포인트

운영 현장에서 장애 발생 후 원인 파악까지 평균 **2~6시간**, 대응 완료까지 **4~10시간** 소요되는 경우가 흔합니다. 숙련 운영자만 상황을 빠르게 복원할 수 있는 구조에서는 야간/교대 시 대응 시간이 더 길어집니다.

`Explainable Operation Intelligence`는 이 대응 시간을 단축하는 것을 목표로 합니다.

- MTTR 감소 (사건 단위 타임라인 제공으로 원인 파악 시간 **50~70% 단축** 목표)
- 고급 운영 인력 의존도 감소 (사건 문맥이 구조화되어 있어 중급 인력도 빠르게 대응 가능)
- 장애 리포트 작성 시간 감소 (사건 요약 자동 생성으로 보고 준비 시간 단축)

## 4.5 `Industrial Data Spine`

### 용어 정의

- **EDA (Equipment Data Acquisition)**: 설비에서 발생하는 센서값, 상태, 이벤트 데이터를 실시간 고속으로 수집하는 시스템입니다. TC가 제어 신호를 주고받는다면, EDA는 그 과정에서 발생하는 데이터를 놓치지 않고 수집하는 역할입니다.
- **FDC (Fault Detection and Classification)**: 수집된 공정 데이터를 분석해 공정 이상을 사전에 감지하고 분류하는 시스템입니다. 불량 발생 전 이상 징후를 파악해 예방적 조치를 가능하게 합니다.

### 고객 문제

많은 TC는 설비 연결과 제어에서 역할이 끝납니다. 그 결과 차후 EDA, FDC, APC, 상위 분석 시스템을 붙일 때 다시 데이터를 정의하고, 다시 수집 경로를 만들고, 다시 정합성을 맞춰야 합니다.

### 적용 방식

`Industrial Data Spine`은 TC를 단일 목적 시스템으로 끝내지 않고, 향후 고속 수집과 분석 시스템이 함께 사용할 수 있는 기준 데이터 축으로 만드는 전략입니다.

핵심 기준 축은 아래와 같습니다.

- EQP (설비)
- Model / Model Version (설비 운용 명세 버전)
- Workflow (공정 흐름 정의)
- Runtime State / Alarm (설비 실시간 상태)
- Work / Carrier / Lot (작업 단위 계층 구조)

이 기준 축을 중심으로 두 방향으로 확장합니다.

1. `EDA 방향`
   - 고속 수집 데이터를 EQP, model version, 상태, 작업 문맥과 함께 연결합니다.
   - TC가 보유한 설비 식별 정보와 작업 문맥이 EDA 데이터의 태깅 기준이 됩니다.
2. `FDC 방향`
   - 원시 데이터만 저장하는 것이 아니라, recipe, chamber, lot, 작업 상태와 정렬된 분석 가능 데이터로 변환합니다.
   - TC의 Work/Lot 계층 구조가 FDC 분석의 컨텍스트 기준이 됩니다.

AI 관점에서 보면 이 항목은 AI가 직접 동작하는 화면이라기보다, `RAG`, 설명형 운영, 이후 분석 기능이 공통으로 기대는 데이터 기반입니다.

### 현재 기반

- `tc_eqp`, `tc_model_version`, `tc_work`를 중심으로 한 도메인 구조
- Work -> ControlJob -> ProcessJob -> Lot의 제조 친화적 계층 모델

### next 단계에서 추가할 것

- 공통 이벤트 / 데이터 계약 표준화
- 분석용 파생 데이터셋
- EDA / FDC 연계용 기준 키와 문맥 매핑
- AI / RAG 지식 베이스가 사용할 수 있는 운영 용어사전과 컨텍스트 매핑

### 고객 관점의 의미

- 차후 EDA / FDC 프로젝트 착수 비용을 낮출 수 있습니다.
- 부서별 데이터 기준을 통일할 수 있습니다.
- 상위 시스템 연동 시 중복 개발을 줄일 수 있습니다.

### 비용 절감 포인트

EDA/FDC 고도화 프로젝트에서 데이터 기반이 없는 경우, 착수 단계에서 데이터 정의와 수집 경로 재구성에만 **수 개월**이 추가로 소요됩니다. `nori-tc`의 기준 데이터 축이 있으면 이 착수 기간을 단축할 수 있습니다.

- 후속 시스템 연동 재개발 비용 감소 (기준 데이터 축이 있어 EDA/FDC 착수 시 데이터 재정의 작업 최소화)
- 데이터 정합성 이슈 대응 비용 감소 (부서 간 기준 데이터가 통일되어 있어 연동 불일치 감소)
- 고도화 프로젝트 기간 단축

## 4.6 `Autonomous Commissioning Lab`

### 고객 문제

현장에서는 개발 완료보다 `라인 투입 전 검증 완료`가 더 중요합니다. 신규 설비나 변경 사항을 실제 라인에 바로 넣고 시험하는 방식은 비용이 크고, 실패 시 생산 영향이 큽니다.

### 적용 방식

`Autonomous Commissioning Lab`은 실라인 반영 전에 가능한 한 같은 엔진으로 먼저 검증하는 사전 검증 환경입니다.

동작 방향은 아래와 같습니다.

1. 신규 설비 명세 또는 변경 명세를 입력합니다.
2. 샘플 로그, 운영 로그, 시뮬레이터 입력을 준비합니다.
3. 같은 gateway runtime, workflow 엔진, 상태 전이 규칙으로 사전 검증을 수행합니다.
4. parser, workflow, action, timeout, start / end 흐름을 검사합니다.
5. 결과를 테스트 결과서로 정리합니다.

여기서 AI는 보조 역할을 가질 수 있습니다.

- 테스트 시나리오 초안 생성
- 누락된 케이스 추천
- 결과 요약과 이상 포인트 설명

하지만 실제 검증 실행은 반드시 실라인과 최대한 동일한 규칙 엔진이 담당해야 합니다.

### 현재 기반

- Gateway runtime control 구조
- async lifecycle 처리 구조
- 모델 / 워크플로 / 설비 상태 기반 구조

### next 단계에서 추가할 것

- 샘플 로그 / 운영 로그 replay 환경
- 시뮬레이터 연계 어댑터
- 명세 기반 테스트 실행기
- 결과서 자동 정리

### 고객 관점의 의미

- 현장 반영 전 검증 수준이 올라갑니다.
- 첫 투입 시 불확실성을 줄일 수 있습니다.
- 고객 내부 승인 프로세스를 더 쉽게 만들 수 있습니다.

### 비용 절감 포인트

실라인 현장 시험은 설비, 인력, 라인 점유 비용이 모두 발생하며, 한 번의 시험 실패 시 재준비에만 수일이 소요되는 경우도 있습니다. 사전 검증 환경이 있으면 이 반복 횟수를 줄일 수 있습니다.

- 현장 시험 반복 비용 감소 (사전 검증에서 주요 오류를 사전에 발견해 현장 시험 횟수 감소)
- 초기 안정화 기간 단축 (첫 투입 품질이 높아져 초기 안정화 기간 단축)
- 설비 반영 후 긴급 대응 비용 감소

## 4.7 AI 인프라 구성과 보안 원칙

### 데이터 보안

`nori-tc`의 AI 기능은 **고객사 설비 문서, 운영 로그, 메시지 데이터를 외부 클라우드로 전송하지 않습니다.**

모든 AI 처리(문서 추출, RAG 검색, LLM 추론, Agent 실행)는 고객사 내부 서버에서 온프레미스(On-Premises) 또는 고객사 전용 폐쇄망 환경에서 수행합니다. 설비 명세, 공정 로그, 모델 데이터는 고객사 네트워크 외부로 나가지 않습니다.

### 추천 LLM 구성

`nori-tc`가 사용하는 AI 기능(문서 명세 추출, workflow 초안 생성, 사건 설명, 운영 대응 요약)은 특수 목적 모델이 아니라, 구조화된 텍스트 생성과 한국어 지원이 우수한 범용 오픈소스 LLM으로 충분히 수행 가능합니다.

현재 서버 GPU 사양이 확정되기 전이므로, GPU 규모별로 선택 가능한 모델 구성을 아래에 정리합니다.

| GPU VRAM | 추천 모델 | 특징 |
|---|---|---|
| 16GB 이상 | Qwen2.5-7B | 한국어/영어/중국어 다국어 지원 우수, 구조화 출력 품질 좋음 |
| 24GB 이상 | Qwen2.5-14B | 7B 대비 명세 추출과 교차 검토 정확도 향상 |
| 40GB 이상 (단일 또는 멀티 GPU) | Qwen2.5-72B / Llama 3.1-70B | 복잡한 문서 교차 분석, 사건 설명 품질 최상 |

**Qwen2.5 시리즈를 1순위로 추천하는 이유**: 한국어와 제조 도메인 용어 이해 품질이 높고, JSON 등 구조화된 형식으로 출력하는 데 강점이 있어 `evidence block` 생성과 명세 초안 생성에 적합합니다.

GPU 사양 확정 후 실제 모델 크기를 선택하며, 필요 시 양자화(Quantization) 적용으로 동일 GPU에서 더 큰 모델을 운영하는 방식도 검토합니다.

### AI 오류 관리 (Hallucination 대응)

LLM이 잘못된 명세나 부정확한 설명을 생성하는 것은 현재 AI 기술의 한계로 항상 발생할 수 있습니다. `nori-tc`는 이 리스크를 제품 설계 수준에서 관리합니다.

- **사람 승인 게이트 필수**: AI가 생성한 명세 초안, 운영 대응 제안은 사람이 검토하고 승인한 후에만 실제 운영에 반영됩니다. AI 단독으로 런타임에 반영하지 않습니다.
- **근거 링크 표시**: AI가 설명을 생성할 때 어떤 로그, 이벤트, 문서 원본을 근거로 했는지 함께 표시합니다. 운영자가 AI 설명을 그대로 수용하지 않고 직접 근거를 확인할 수 있습니다.
- **추정 명시**: 근거가 부족한 부분은 `추정`으로 명확히 표시하거나 운영자 확인 질문으로 전환합니다. AI가 모르는 것을 아는 것처럼 표현하지 않습니다.

## 5. 일반적인 TC 대비 nori-tc의 차이

| 구분 | 일반적인 TC | nori-tc |
|---|---|---|
| 신규 설비 대응 | 문서 해석 후 수작업 개발 중심 | 원본 문서 입력 -> evidence 정규화 -> 명세 초안 -> 검토/승인 -> 구현 |
| 변경 관리 | 운영 반영 전 수동 점검 중심 | 버전 분리, diff, 영향도, 사전 검증, 단계 반영, 복귀 절차 |
| 안정성 설명 | “안정적”이라는 표현 위주 | partition, 응답 수집, 비동기 trace, DLQ, 발송 이력 구조를 근거로 설명 |
| 장애 대응 | 로그 검색과 숙련 인력 의존 | trace, 상태, workflow, 작업 이력 기반 사건 단위 설명 |
| 고도화 확장 | TC 자체에 머무름 | EDA/FDC/AI 활용까지 이어지는 기준 데이터 축 제공 |

`nori-tc`의 차별점은 단순히 기능 수가 많다는 점이 아니라, 같은 TC 기능을 `더 검증 가능하게`, `더 운영 가능하게`, `더 확장 가능하게` 만드는 방향에 있습니다.

## 5.1 시장에 TC 제품은 많습니다. 그럼에도 nori-tc를 선택해야 하는 이유

TC 시장에는 이미 오랜 경험을 가진 제품들이 존재합니다. 고객 입장에서 새로운 TC를 선택하는 것은 단순 기능 비교가 아닌, **향후 운영 비용과 확장 가능성**을 함께 판단해야 하는 결정입니다.

현재 시장의 주요 TC 솔루션 구도는 아래 네 가지입니다.

### 시장 구도 이해

**① 설비 OEM 측 도구 — Cimetrix (PDF Solutions), PEER Group, 코닉오토메이션 EasyCluster**

Cimetrix와 PEER Group은 전 세계 300mm 팹에 납품되는 설비(OEM 장비 제조사)의 내부에 탑재되는 TC 소프트웨어입니다. 코닉오토메이션 EasyCluster도 동일하게 국내 설비 OEM 중심입니다.

이 제품들은 **설비 측(장비 제조사)** 에서 동작하는 솔루션입니다. 팹 운영자(고객사)가 직접 설비 온보딩, 변경 관리, 운영 절차를 제어하는 호스트 측 역할은 담당하지 않습니다. 즉, 이 제품들은 `nori-tc`와 대체 관계가 아니라 **보완 관계**입니다. 다만, 고객사가 팹 운영자 입장에서 사용하는 TC 기능은 별도로 필요합니다.

**② 엔터프라이즈 MES 패키지 — IBM SiView, Siemens Opcenter Execution Semiconductor**

IBM SiView와 Siemens Opcenter는 TC가 MES 전체 패키지의 일부 모듈로 포함된 형태입니다. 200개 이상의 사전 정의된 시나리오(MRM), 글로벌 대형 팹 레퍼런스를 보유하지만, **TC만 단독 도입하기 어렵고** 전체 플랫폼 구축에 수억 원 이상의 초기 투자와 수년의 구축 기간이 동반됩니다. 운영 유연성이 낮고, 커스터마이징 비용이 높습니다.

**③ 국내 통합 플랫폼 — 에임시스템 Nexbe+ EAS**

에임시스템 Nexbe+는 한국 반도체·디스플레이 현장에서 20년 이상 레퍼런스를 보유한 MES + EAS + MCS 통합 플랫폼입니다. LG디스플레이 등 국내 대형 고객사에 적용된 실적이 있습니다.

단, 아래 한계가 있습니다.

- MES 전체와 묶여 있어 TC 기능만 선택 도입이 어렵습니다.
- 신규 설비 온보딩은 여전히 수작업 문서 해석과 엔지니어링 서비스 의존 방식입니다.
- 변경 관리와 메시지 신뢰성 증명 기능이 구조화된 운영 절차로 제품에 내재되어 있지 않습니다.
- AI 기반 운영 기능은 공개 자료 기준으로 확인되지 않습니다.

**④ 자체 개발 TC**

삼성전자, SK하이닉스처럼 대형 팹은 공정 노하우 보호와 유연성을 위해 TC를 자체 개발합니다. 이 방식은 완전한 맞춤 구현이 가능하지만, 수백 명 규모의 내부 개발·운영 조직이 필요하고, 이직과 조직 변화에 따른 지식 단절 리스크가 있습니다. 중견 팹이나 신규 라인에서는 현실적으로 선택하기 어렵습니다.

---

### nori-tc가 이 구도에서 다른 점

`nori-tc`는 **팹 운영자 측에서 직접 설비를 제어하고 운영하는 TC**입니다. 설비 OEM 제품처럼 장비 내부에 탑재되는 것이 아니라, **고객사가 여러 설비를 연결하고 운영하는 중심축**에 위치합니다.

아래 표는 고객사가 실제로 겪는 운영 비용 구간별로 기존 솔루션과 `nori-tc`를 비교한 것입니다.

| 비교 항목 | Cimetrix / PEER (설비 OEM 측) | 에임시스템 Nexbe+ EAS | IBM SiView / Siemens Opcenter | nori-tc |
|---|---|---|---|---|
| **주요 역할** | 설비 내부 SECS/GEM 연결 | MES+EAS 통합 플랫폼 | MES 전체 패키지 (TC 포함) | 팹 운영자 측 TC 및 운영 플랫폼 |
| **TC 단독 도입** | 해당 없음 (설비 OEM용) | MES 전체와 묶여 어려움 | TC만 분리 불가 | 가능 |
| **신규 설비 온보딩** | 설비 제조사에서 사전 탑재 | 엔지니어링 서비스 + 수작업 | MRM 시나리오 적용 | 원본 문서 → evidence → 명세 초안 → 승인 흐름 제공 |
| **변경 관리 구조** | 해당 없음 | 미확인 (공개 자료 없음) | NPI 변경 관리 내장 (비용 높음) | diff + 영향도 + 단계 반영 + 복귀 절차 내장 |
| **메시지 처리 신뢰성 증명** | 설비 측 연결 신뢰성 중심 | 국내 대형 팹 검증 경험 | 엔터프라이즈 24x7 운영 | partition 라우팅 + DLQ + 발송 이력 + 처리 근거 추적 |
| **AI 기반 운영 기능** | 분석 플랫폼 별도 연계 (Exensio) | 공개 자료 기준 없음 | 디지털 트윈, SPC 내장 | 온프레미스 LLM + RAG로 운영 내부 기능으로 제공 |
| **EDA/FDC 연계** | CIMPortal+로 데이터 수집 제공 | 미확인 | FDC·SPC 내장 | TC 운영 시점부터 기준 데이터 축 구성 |
| **도입 비용 구조** | OEM 라이선스 (장비 구매 시 포함) | 구축 + 운영 통합 계약 | 엔터프라이즈 계약 (고비용) | TC 기능 단독 도입 가능 |
| **운영 인력 의존도** | 설비 제조사 의존 | 엔지니어링 서비스 의존 | 내부 운영팀 필요 | 변경 관리·장애 대응의 구조적 의존도 낮춤 |

### 정리

`nori-tc`를 선택해야 하는 상황은 아래와 같습니다.

- 엔터프라이즈 MES 전체 패키지 없이 **TC 기능 중심으로 도입**하고 싶은 경우
- 신규 설비 도입 속도와 운영 변경 안정성을 **제품 기능 수준에서** 확보하고 싶은 경우
- AI 기반 운영 기능을 **외부 플랫폼 연계 없이** TC 운영 흐름 안에서 사용하고 싶은 경우
- 이후 EDA/FDC 고도화를 **다시 데이터를 재정의하지 않고** 이어가고 싶은 경우
- 운영 인력 숙련도 의존을 낮추고 **대응 가능한 인력 범위를 넓히고** 싶은 경우

## 5.2 시장 유형별 경쟁사 상세 분류

> 5.1에서는 글로벌·엔터프라이즈 경쟁사를 포지션 기준으로 요약했습니다. 본 섹션에서는 국내외 TC·CIM 제품을 프로토콜과 역할 계층 기준으로 상세 분류합니다.

### 시장 구조 이해

TC(Tool Control) 시장은 단일하지 않습니다. 프로토콜 기반에 따라 두 개의 시장이 사실상 분리되어 있습니다.

**SECS/GEM 기반 TC 시장**은 반도체·디스플레이 팹을 중심으로 형성되어 있고, 업계 표준이 있기 때문에 제품화가 가능했습니다. 대형 솔루션부터 툴킷까지 다양한 제품이 존재합니다.

**Non-SECS TC 시장**은 이차전지, PCB, 일반 제조업 라인 중심으로, Socket Custom Protocol, Modbus RTU/TCP, OPC UA 등 설비마다 프로토콜이 다릅니다. 표준이 없기 때문에 "제품"이 아닌 "SI 개발 방식"으로 존재합니다. 검색해도 제품명이 잘 안 나오는 이유가 바로 이 시장 구조 때문입니다.

`nori-tc`는 이 두 시장을 모두 커버하는 포지션입니다.

---

### 경쟁사 분류

총 14개 경쟁 포지션을 4개 유형으로 분류합니다.

- **유형 1 — SECS/GEM 기반 TC·MES 플랫폼**: 자체개발/SI 커스텀 TC, 미라콤아이앤씨 Nexplant MESplus, eInnoSys EIGEMHost 등 SECS 툴킷, 범용 SCADA (Ignition, AVEVA)
- **유형 2 — Non-SECS CIM/TC 플랫폼형** (nori-tc와 가장 직접적 경쟁): 씨아이엠플러스 CIMStudio, 에이아이엠 AIM FMS/CIM, 이노아이티 Inno-CIM, 와이솔루션 W-CIM, 인사이트온 PbotEngine, 엠아이큐브솔루션 MES+EES
- **유형 3 — 게이트웨이·브릿지형** (연결 레이어만 제공): 링크제니시스 XGate/Non-SECS Gateway, 두어 ECP, 디로직 Equipment Control Bridge, 사이너스텍 ACS, 티와이즈 Non-SECS Converter
- **유형 4 — EQP 제어 레이어** (TC와 레이어 다름): 소프트모션앤로보틱스 WMX3

### 핵심 메시지

중소·중견 팹의 TC는 대부분 자체 개발이거나 SECS/GEM SDK 위에 직접 쌓는 방식, 또는 Non-SECS 환경에서 SI 개발 방식으로 운영됩니다. 기존 CIM/TC 제품들은 "설비를 상위 시스템에 연결"하는 문제는 해결하지만, 그 이후의 운영 구조를 다루지 않습니다.

진짜 비용은 도입 당시가 아닙니다. 신규 설비 도입 때마다 반복되는 개발 공수, 담당자 퇴사 후의 지식 단절, 변경 실패 한 번의 라인 중단 비용, 장애 발생 시 원인 추적에 소요되는 MTTR이 나중에 청구됩니다.

`nori-tc`는 연결 이후의 운영 구조, 즉 변경이 통제되고, 메시지 신뢰성이 증명되며, 장애 원인이 추적 가능하고, AI가 운영을 보조하는 라인 실행 플랫폼입니다.

## 6. 고객사가 도입했을 때 기대하는 효과

### 6.1 신규 설비 도입

- 설비 문서 해석 시간 단축
- parser / workflow / 테스트 준비 시간 단축
- 벤더 확인 질문과 누락 항목 정리 체계화

### 6.2 운영 변경

- 변경 전 검증이 강화되어 사고 확률 감소
- 사고 발생 시 복귀와 원인 추적이 빨라짐
- 변경 승인 / 리뷰 절차의 근거가 명확해짐

### 6.3 장애 대응

- MTTR 감소
- 유실 / 중복 / 반쪽 처리 의심 건 조사 시간 감소
- 숙련 운영 인력 의존도 감소

### 6.4 장기 고도화

- EDA / FDC 연계 비용 감소
- 데이터 재정의와 중복 수집 비용 감소
- 상위 시스템 도입 시 기간 단축

### 6.5 도입 방식과 기존 시스템 전환

`nori-tc`는 기본적으로 **신규 라인 도입** 또는 **TC 교체 시점**을 주요 도입 경로로 상정합니다. 이 경우 기존 레거시 TC와의 충돌 없이 처음부터 `nori-tc` 기반으로 설비 연결, 모델 정의, 운영 절차를 구성할 수 있습니다.

기존 TC에서 전환하는 경우에는 아래 순서로 진행합니다.

1. **설비 모델 / 파라미터 이관**: 기존 운영 중인 설비 정의, 메시지 규칙, 파라미터를 `nori-tc` 스키마로 매핑합니다. `Spec-to-Proof`의 문서 추출 기능을 이 작업에 그대로 활용할 수 있습니다.
2. **병행 운영 기간**: 핵심 설비는 기존 TC와 `nori-tc`를 일정 기간 병행 운영하며 동작을 검증합니다.
3. **단계적 절체**: `Verified ChangeOps`의 단계 반영 개념과 동일하게, 설비 그룹 단위로 순차적으로 전환합니다. 전체 라인을 한 번에 전환하지 않습니다.
4. **운영 이관 완료**: 검증 완료된 설비 그룹부터 기존 TC 연결을 해제하고 `nori-tc`로 단독 운영합니다.

전환 과정에서 기존 설비 문서와 운영 이력은 `nori-tc` 내부의 기준 데이터로 흡수되어, 이후 AI 기능의 RAG 기반 지식으로도 활용됩니다.

## 7. 결론

`nori-tc`의 제안 포인트는 단순 통신 기능 추가가 아닙니다.

핵심은 아래 여섯 가지입니다.

- 원본 설비 문서를 검토 가능한 명세로 더 빠르게 전환하는 것 (`Spec-to-Proof`)
- 운영 중 변경을 더 안전하게 다루는 것 (`Verified ChangeOps`)
- 메시지와 처리 결과를 근거 기반으로 설명할 수 있게 만드는 것 (`Provable Reliability`)
- 장애 대응을 사건 단위로 더 쉽게 만드는 것 (`Explainable Operation Intelligence`)
- 이후 EDA / FDC / AI 활용으로 자연스럽게 이어질 수 있는 데이터 축을 만드는 것 (`Industrial Data Spine`)
- 실라인 반영 전 동일한 엔진으로 사전 검증하는 것 (`Autonomous Commissioning Lab`)

따라서 `nori-tc`는 단순 연결 시스템이 아니라, 라인 실행 리스크를 낮추고 이후 생산 고도화의 기반을 만드는 실행 플랫폼으로 제안되어야 합니다.

도입 검토 단계에서 기술 실사가 필요하시면 아래 항목에 대한 상세 자료를 별도로 제공드릴 수 있습니다.

- 모델 버전 관리 API 명세
