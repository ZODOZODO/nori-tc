# 09. Mailbox 기반 설비 단위 직렬 처리 (Mailbox Sequential Processing)

## 적용 앱

- `tc-comm-gateway-app`
- `tc-business-core-app`

---

## 개요

**Mailbox 패턴**은 설비(Equipment) 단위로 메시지를 순서대로 처리하기 위한 구조입니다.

각 설비는 자신만의 **메일박스(Mailbox)** 를 가지고 있습니다.
메일박스는 편지함처럼 메시지를 쌓아두고 순서대로 꺼내서 처리합니다.
서로 다른 설비의 메일박스는 **동시에(병렬로)** 처리할 수 있습니다.

---

## 왜 이 패턴이 필요한가?

### 문제 1: 같은 설비의 메시지가 순서 없이 처리되면?

```
시나리오: EQP-001 설비에 명령 3개가 연속 도착

명령 A: 레시피 설정
명령 B: 처리 시작
명령 C: 상태 조회

만약 병렬로 처리하면:
  스레드 1: 명령 B 처리 시작 (레시피 설정 전에 처리 시작!)
  스레드 2: 명령 A 처리 (레시피 설정)
  → 잘못된 레시피로 처리가 시작되는 위험

직렬로 처리하면:
  A → B → C 순서 보장
  → 올바른 레시피로 처리 시작
```

### 문제 2: 스레드 하나로 모든 설비를 처리하면?

```
스레드 하나: EQP-001 → EQP-002 → EQP-003 → EQP-001 → ...
  → 설비 하나의 처리가 오래 걸리면 다른 설비도 모두 대기
  → 100개 설비가 있으면 99개가 기다려야 함
  → 처리 성능이 매우 낮아짐
```

### 해결: 설비별 독립 메일박스 + 다중 Worker

```
메일박스 A (EQP-001): [명령A1] [명령A2] [명령A3]  ←→  Worker 1
메일박스 B (EQP-002): [명령B1] [명령B2]           ←→  Worker 2
메일박스 C (EQP-003): [명령C1]                    ←→  Worker 3
메일박스 D (EQP-004): [명령D1] [명령D2]           ←→  Worker 1 (재사용)

→ 각 설비 내부: 순서 보장 (직렬)
→ 설비 간: 동시 처리 (병렬)
→ Worker N개가 M개의 설비를 처리
```


## Gateway에서의 구현

### 핵심 컴포넌트

| 클래스 | 역할 |
|--------|------|
| `EquipmentMailboxRegistry` | 설비별 메일박스를 생성하고 관리하는 레지스트리 |
| `EquipmentProcessingCoordinator` | Worker 스레드 풀을 관리하고 메일박스를 스케줄링 |
| `EqpSequentialProcessor` | 하나의 설비에 대한 메시지를 순서대로 처리 |

### 처리 흐름

```
1. Kafka 또는 Netty에서 메시지 수신
         ↓
2. eqpId 추출
         ↓
3. EquipmentMailboxRegistry.getOrCreate(eqpId)
   → 해당 설비의 메일박스 조회 (없으면 새로 생성)
         ↓
4. 메일박스 큐에 메시지 enqueue
   (큐 가득 찼으면 → overflow 처리 → DLQ)
         ↓
5. EquipmentProcessingCoordinator가 idle Worker에 메일박스 할당
         ↓
6. Worker: 메일박스에서 메시지 drain (최대 64개씩)
         ↓
7. EqpSequentialProcessor: 각 메시지를 순서대로 처리
         ↓
8. 처리 완료 → Worker idle 상태로 복귀
```

### 설정

```properties
# tc-comm.properties
tc.comm.gateway.worker-threads=8          # Worker 스레드 수
tc.comm.gateway.inbound-queue-capacity=2048  # 메일박스 큐 용량
# maxChunksPerDrain=64 (1번에 최대 64개 메시지 처리)
```

## Business Core에서의 구현

### 핵심 컴포넌트

| 클래스 | 역할 |
|--------|------|
| `BusinessRuntimeEngine` | 3단계 큐 전체를 관리하는 메인 엔진 |
| `MailboxScheduler` | 설비별 메일박스를 Worker에게 스케줄링 |
| `MailboxExecutionRuntime` | Worker 스레드 풀로 메일박스 실행 |

### Business Core의 3단계 큐 구조

```
┌───────────────────────────────────────────────────────────────┐
│ 1단계: Topic Queue (Kafka Consumer → Runtime)                 │
│                                                               │
│  topic: tc.eqp.events     [메시지] [메시지] [메시지] ...     │
│  topic: tc.mes.events     [메시지] [메시지] ...              │
│  topic: tc.ui.events      [메시지] ...                       │
└───────────────────────────────┬───────────────────────────────┘
                                ↓ eqpId 기반 분류
┌───────────────────────────────────────────────────────────────┐
│ 2단계: Mailbox Queue (설비별 분류)                            │
│                                                               │
│  Mailbox(EQP-001): [작업1] [작업2] [작업3]                   │
│  Mailbox(EQP-002): [작업1] [작업2]                           │
│  Mailbox(EQP-N):   [작업1]                                   │
└───────────────────────────────┬───────────────────────────────┘
                                ↓ Worker 할당
┌───────────────────────────────────────────────────────────────┐
│ 3단계: Worker Pool (실제 비즈니스 처리)                       │
│                                                               │
│  Worker 1: EQP-001 메시지 처리                               │
│  Worker 2: EQP-002 메시지 처리                               │
│  Worker N: ...                                               │
└───────────────────────────────────────────────────────────────┘
```

### 설정

```properties
# tc-business-core.properties
tc.business.core.runtime.dispatcher-threads=4    # 메일박스 스케줄링 스레드
tc.business.core.runtime.worker-threads=8        # 실제 처리 Worker 수
tc.business.core.runtime.topic-queue-capacity=5000   # Topic Queue 용량
tc.business.core.runtime.mailbox-capacity=10000      # 메일박스 큐 용량
```

## 핵심 설계 원칙

| 원칙 | 내용 |
|------|------|
| **같은 설비, 다른 스레드 금지** | 동일한 eqpId의 메시지는 절대 동시에 다른 스레드에서 처리하지 않습니다 |
| **설비 간 독립** | EQP-001의 처리가 느려도 EQP-002는 영향받지 않습니다 |
| **Bounded Queue** | 메일박스 큐 크기가 제한되어 있어 메모리 무한 증가를 방지합니다 |
| **Overflow 처리** | 큐가 가득 차면 새 메시지를 DLQ로 보냅니다 (메시지 유실 없음) |

---

## 처리 순서 보장 예시

```
시간 →  0ms    10ms   20ms   30ms   40ms

EQP-001: [A] → [B] → [C]    (순서 보장: A → B → C)
EQP-002:       [X] → [Y]    (순서 보장: X → Y)
EQP-003: [P]         [Q]    (순서 보장: P → Q)

→ EQP-001과 EQP-002는 동시에 처리
→ 같은 설비 내에서는 반드시 순서 보장
```

## 주의사항

| 항목 | 내용 |
|------|------|
| **큐 용량 설정** | `inbound-queue-capacity`가 너무 작으면 트래픽이 몰릴 때 DLQ가 많이 발생합니다. 설비 수 × 예상 동시 메시지 수를 고려해서 설정하세요 |
| **Worker 수 설정** | `worker-threads`는 CPU 코어 수와 I/O 비율을 고려해서 설정합니다. I/O가 많으면 코어 수보다 많이 설정해도 됩니다 |
| **처리 시간 모니터링** | 특정 설비의 메시지 처리 시간이 길면 해당 설비의 큐가 계속 쌓입니다. 처리 지연을 모니터링하세요 |
| **초기 메일박스 생성** | 앱 기동 시 모든 설비의 메일박스가 미리 생성되지 않고, 첫 메시지가 도착할 때 생성됩니다 |
